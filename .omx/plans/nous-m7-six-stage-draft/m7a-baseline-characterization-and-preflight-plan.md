# M7A Plan: Baseline Characterization and Dependency Preflight

Status: Draft execution plan

Date: 2026-08-08

Depends on: M1-M6 on `main`

Unlocks: M7B Read-Only Nous Core

Umbrella PRD: `prd-m7-agent-ready-core-and-mcp.md`

Shared rules: `m7-shared-contract.md`

Verification contract: `test-spec-m7a-baseline-characterization-and-preflight.md`

## 1. Objective

Freeze the current M2-M6 operator-visible behavior before moving implementation into a shared core, and prove that the official Ruby MCP SDK, stable protocol target, local stdio transport, and intended Codex client environment are feasible.

M7A is deliberately conservative. It should produce better tests and an explicit dependency decision, not new product behavior.

## 2. Why This Stage Exists

The existing scripts are both interfaces and implementations. A refactor can accidentally change:

- accepted arguments;
- date/environment precedence;
- error wording and prefixes;
- output path resolution;
- collision suffix allocation;
- frontmatter/body formatting;
- review routing;
- generated byte ordering;
- failure cleanup.

Without characterization, later failures are ambiguous: the new core may be wrong, or an old assumption may never have been documented. M7A turns implicit behavior into an executable contract before extraction.

MCP also introduces an external dependency into a repository that currently uses Ruby standard library only. The dependency and transport must be proven before product code is designed around them.

## 3. Requirements Summary

M7A must:

1. verify the working tree is safe and contains no private payload;
2. record the local Ruby, RubyGems, and Bundler versions;
3. run every current direct test, `make test`, and `make lint` before modification;
4. add focused characterization coverage for current CLI surfaces not already locked;
5. record deterministic baseline outputs for graph/report and representative note generation using synthetic temporary fixtures;
6. prove the official Ruby MCP SDK can initialize a minimal tools-only stdio server with the intended stable protocol;
7. prove a raw JSON-RPC client can initialize and list tools without stdout contamination;
8. attempt Codex CLI discovery/call against the throwaway server when the local Codex surface is available;
9. document the selected SDK/protocol/runtime decision and any unresolved compatibility issue;
10. leave product scripts and vault behavior unchanged.

## 4. Scope

### 4.1 In scope

- Existing CLI behavior characterization.
- Synthetic temporary-vault fixtures.
- A dedicated test such as `scripts/test_cli_contracts.rb` if that keeps the contract clear.
- Minimal extensions to existing M2-M6 tests where behavior is already naturally owned there.
- Temporary SDK preflight in a throwaway directory.
- An ADR or decision note recording:
  - Ruby version;
  - Bundler version;
  - selected official `mcp` gem version;
  - required Ruby version;
  - protocol version;
  - stdio proof result;
  - raw framing proof result;
  - Codex integration proof result or reason it was not testable;
  - transitive dependency summary.
- Makefile/signpost updates only when a committed test or decision file requires them.

### 4.2 Out of scope

- `lib/nous` implementation.
- Moving any business logic.
- Shared locks or atomic writer changes.
- Agent read or write operations.
- Candidate metadata/schema changes.
- Committed `Gemfile` or `Gemfile.lock`.
- Product MCP server.
- Frontend, HTTP, model calls, embeddings, database, watcher, voice, or OCR.

## 5. Mandatory Assumptions

- The current `main` branch is the behavioral baseline unless an existing test already fails.
- Product-owned messages are contracts; incidental Ruby exception text is not.
- Tests use temporary synthetic data only.
- SDK installation may require network during preflight, but the resulting Nous server must be runtime-offline.
- Current observed planning baseline is the official `mcp` gem `1.0.0` with Ruby `>= 2.7.0` and stable protocol `2025-11-25`; execution must reverify these facts.
- If the local Ruby runtime is incompatible with the current official SDK, stop and present supported options. Do not switch language or SDK silently.

## 7. Acceptance Criteria

### 7.1 Baseline health

- All five current direct tests exit zero before changes.
- `make test` exits zero before changes.
- `make lint` exits zero before changes.
- `git diff --check` is clean.
- `git status --short` is understood and contains no private artifact.

### 7.2 CLI characterization

For each current script, tests lock:

- help behavior;
- positional argument count;
- option parsing failures;
- environment-variable/explicit-option precedence;
- default vault/output behavior;
- alternate vault/output behavior;
- success stdout prefix and path form;
- stderr command prefix;
- nonzero status on expected failure;
- no stack trace for handled domain failures;
- fixed-time determinism where supported;
- no partial overwrite on validated failure.

### 7.3 Output baseline

Using fixed times and synthetic fixtures:

- representative text artifact and draft Markdown bytes are recorded/asserted;
- representative M6 payload/artifact/draft path coordination is asserted;
- review approval/rejection metadata is asserted;
- graph JSON bytes are deterministic;
- Nous report Markdown bytes are deterministic;
- review queue report bytes/ordering are deterministic where the current contract defines them.

Prefer explicit assertions over large opaque snapshots. When byte fixtures are used, explain why byte identity is part of the product contract.

### 7.4 SDK preflight

- The official SDK source and gem identity are verified.
- Exact selected gem version is recorded.
- Required Ruby version is recorded and satisfied.
- Minimal tools-only stdio server starts.
- Initialize succeeds using the selected stable protocol.
- `tools/list` succeeds.
- One synthetic read-only tool call succeeds.
- Every nonempty stdout line/frame is valid protocol JSON.
- Diagnostics use stderr.
- No listener socket is opened.
- No API key is needed.
- A raw client independently validates the handshake.
- Codex CLI discovery/call is tested or marked untestable with the exact missing prerequisite.
- The throwaway server and gems are not committed as product code.

### 7.5 Completion

- Characterization tests pass after their addition.
- Existing direct tests still pass.
- `make test` and `make lint` pass.
- The ADR/preflight record contains no secret or private path.
- No M7B-M7F product implementation is present.

## 8. Detailed Implementation Steps

### Step 1: Inspect repository and privacy state

Run:

```sh
git status --short
git diff --check
git ls-files
find vault -type f -maxdepth 6 -print
```

Do not print or inspect personal payload content unnecessarily. The purpose is to identify tracked/untracked files and confirm no real data will be swept into a commit.

Record only sanitized findings.

### Step 2: Record runtime inventory

Run and record:

```sh
ruby --version
gem --version
bundle --version
which ruby
which bundle
```

Do not commit full home-directory paths. Record version values and runtime manager name only when useful.

If Bundler is unavailable, determine whether it can be installed without altering unrelated global state. Do not continue to product MCP work in M7A.

### Step 3: Prove the existing baseline

Run in this order:

```sh
ruby scripts/test_ingest_text.rb
ruby scripts/test_ingest_artifact.rb
ruby scripts/test_review_queue.rb
ruby scripts/test_export_graph.rb
ruby scripts/test_generate_nous_report.rb
make test
make lint
```

If any command fails before changes:

1. preserve the failure output;
2. determine whether it is environment-specific or a repository regression;
3. stop M7A feature work;
4. report the blocker rather than changing expectations to obtain green.

### Step 4: Inventory user-visible CLI contracts

For each script, write down:

- usage banner;
- supported options;
- positional rules;
- environment variables;
- success stdout lines;
- error stderr prefix;
- default output path;
- custom path semantics;
- time/date behavior;
- collision behavior;
- rollback/overwrite behavior.

Cross-check README, tests, implementation, and architecture docs. When they disagree, current tested implementation is the baseline, and the discrepancy is documented for product review rather than silently “corrected.”

### Step 5: Add missing characterization coverage

Prefer a dedicated `scripts/test_cli_contracts.rb` for cross-cutting presentation contracts. It should invoke scripts as subprocesses through `Open3.capture3`, not call future core code.

Avoid brittle assertions on:

- Ruby version-specific parser wording;
- temporary directory names;
- incidental ordering not promised by the product;
- stack traces from unhandled programmer bugs.

Assert product-owned values exactly:

- usage first line;
- success prefix;
- command error prefix;
- documented path relation;
- documented metadata fields;
- deterministic bytes with fixed time.

### Step 6: Produce fixed synthetic baselines

Use `Dir.mktmpdir` and synthetic content. Include:

```text
Synthetic M7 baseline fixture.
I turn uncertainty into small systems.
```

Generate and assert:

- M2 artifact/draft;
- M6 writing and binary-image import shapes;
- a reviewed note and claim through review actions;
- a canonical relationship with valid endpoints;
- graph/report outputs with fixed timestamps.

Do not store absolute temp paths in expected fixtures. Normalize or assert vault-relative paths.

### Step 7: Perform SDK identity and dependency verification

Verify the package is the official `modelcontextprotocol/ruby-sdk` gem named `mcp`, not an unrelated MCP package.

In a temporary directory:

1. create a temporary Gemfile pinned to the selected exact version;
2. run Bundler without modifying repository dependency files;
3. record the resolved dependency tree;
4. check gem metadata and required Ruby version;
5. inspect the official SDK README/API for stdio server construction, protocol pinning, tool schemas, structured content, and result validation.

Stop if:

- the gem cannot install on the runtime;
- the official SDK no longer supports stdio;
- the intended stable protocol is unsupported;
- a transitive dependency introduces an unacceptable runtime/service assumption.

### Step 8: Build a throwaway minimal stdio proof

The proof server must:

- live outside product paths or be removed before completion;
- expose one read-only synthetic tool;
- declare tools capability only;
- pin the selected stable protocol;
- return structured content;
- write no banner to stdout;
- open no network socket.

Test it with:

- the official Ruby client;
- a small raw JSON-RPC stdio harness that sends initialize, initialized notification, tools/list, and tools/call.

The raw harness exists to catch issues hidden when client and server share the same SDK.

### Step 9: Check Codex CLI integration

When Codex CLI and its MCP configuration surface are available:

- register the throwaway server using a temporary/project-local test configuration when supported;
- verify discovery;
- invoke the synthetic tool;
- remove the temporary configuration;
- confirm no global user configuration was unintentionally changed.

When unavailable, record:

- command/version checked;
- missing capability or configuration knowledge;
- what M7F must verify later.

Do not claim integration success from SDK-only tests.

### Step 10: Record ADRs

The architecture ADR should state:

- core below CLI/MCP/future frontend;
- MCP is not the frontend backend;
- candidate-only agent writes;
- stdio/tools-only boundary;
- no model runtime inside Nous.

The preflight ADR should state:

- tested date;
- runtime versions;
- exact SDK and protocol;
- proof commands/results;
- dependency summary;
- Codex result;
- known caveats;
- explicit requirement to revalidate in M7F.

### Step 11: Wire checks and signposts

If `scripts/test_cli_contracts.rb` is added:

- add it to `make test` after existing M2-M6 tests or at the beginning as a baseline suite;
- update `scripts/AGENT.md`;
- preserve current test order unless there is a documented reason.

Add/update signposts for any new committed directory/file as required by repository lint.

### Step 12: Final M7A verification

Run focused tests, then all existing tests, lint, diff check, and worktree/privacy inspection. Confirm no core/MCP product files were introduced.

## 9. Codex Potholes and Prohibitions

Codex must not:

- begin extracting shared helpers “while already in the tests”;
- add `Gemfile`/`Gemfile.lock` to the repository in M7A;
- commit a spike server as the real server;
- hand-roll the eventual MCP implementation based on the spike;
- switch to Node/Python after a Ruby incompatibility;
- use an unofficial gem with a similar name;
- modify current scripts to make characterization easier;
- regenerate expected files using the new behavior after accidentally changing it;
- assert machine-specific absolute paths;
- store command logs containing personal paths;
- weaken or delete current tests;
- add frontend/API/model/search scope.

## 10. Risks and Mitigations

### Risk: Characterization locks a bug forever

Mitigation: Lock only user-visible current behavior needed for compatibility. Document suspected defects separately. A bug fix requires an explicit behavior-change decision, not a silent refactor.

### Risk: Snapshot tests become unreadable

Mitigation: Prefer field-level assertions. Use byte fixtures only for graph/report determinism and carefully bounded representative Markdown.

### Risk: Dependency facts change before M7F

Mitigation: Treat M7A as feasibility proof and repeat it immediately before M7F.

### Risk: SDK-only client/server tests agree on the same mistake

Mitigation: Include a raw JSON-RPC stdio harness.

### Risk: Codex modifies global client configuration

Mitigation: Use temporary/project-local configuration and verify cleanup. Do not automate global config writes without explicit user approval.

### Risk: Existing repository already has failing tests

Mitigation: Stop and report. Do not conflate baseline repair with M7A unless separately approved.

## 12. Definition of Done

M7A is done when current behavior is executable and explicit, the official Ruby MCP/stdout path is proven or blocked with a precise incompatibility report, all existing checks are green, and the repository contains no implementation belonging to M7B-M7F.

## 13. Suggested Handoff

Use one owner. The task is small enough that parallel implementation creates more coordination cost than value.

Recommended reasoning: high for verification, medium for test additions.

Handoff message:

```text
Implement M7A only. Freeze the current contracts and prove SDK/stdio feasibility.
Do not add Nous Core, product MCP code, Gemfile, candidate operations, locking,
frontend, or model calls. Stop if the existing baseline is not green or the
Ruby SDK/protocol is incompatible. Leave every M2-M6 test green.
```
